# Fedora 45 testing repository

Fedora 44 keeps `44/testing/aarch64` and `44/stable/aarch64`. Fedora 45 adds
`45/testing/aarch64` only. `aurora-repos` uses `$releasever`, so the same repository
definition selects the matching Fedora release. The production signing key is
unchanged.

## Build inputs

`scripts/build-rpm` selects the native Fedora release from the container's RPM
macros and checks any `AURORA_FEDORA_RELEASE` assertion against it. Fedora 44 uses
the existing top-level recipes and `sources.json`. Fedora 45 uses those same
inputs with files in `packages/<name>/f45/` overlaid where present. Each overlay's
`sources.json` replaces only its named source pins. Build receipts record the
selected files, including the release-specific pins, and identify Fedora 45.

The graphics overlays reuse Ryan's candidates from [PR #90](https://github.com/aurora-silicon/fedora-aurora/pull/90):
Mesa commit `9fe179df8bf1cec359d9e452fc9dfa8680285698`, epoch 1, release 14, the
matching FEX guest and Flatpak GL recipe. The Flatpak builder uses the same
release-specific Mesa source pin. Fedora 45 exports also retain `aurora_dri.so` as a relative alias
to the Asahi loader in the candidate's DRIL layout; all payload checks remain
required. Fedora 44 retains its existing Mesa commit,
release and capabilities.

The Mutter overlay reuses `packages/mutter/f45` from [PR #74](https://github.com/aurora-silicon/fedora-aurora/pull/74),
including its current 51.1 release 5 and patches. The existing Touch ID and UPower
Fedora 45 workflows are also reused by `rpms.yml`: they consume its exact
Fedora 45 artifacts and run their existing upgrade/rollback tests, without
rebuilding those candidates. Standalone runs retain their original build path. The
Plymouth recipe is already the Fedora 45 carry. The release-identity overlay
supplies Fedora 45's identity files, RPM macros and dependency capabilities.
U-Boot's host signing tools use Fedora 45's
[OpenSSL 3 compatibility development packages](https://packages.fedoraproject.org/pkgs/openssl3/openssl3-devel-engine/)
so their existing ENGINE API remains available alongside the system's OpenSSL 4.
The U-Boot target configuration is unchanged. Fedora 44 keeps its original
OpenSSL development dependencies.
The AVD firmware overlay selects Fedora 45's
[versioned LLVM 22 compiler](https://packages.fedoraproject.org/pkgs/llvm22/clang22/),
linker and binary tools. The existing checker still requires all eight qualified
firmware hashes, sizes, linked ELF images and reset vectors. Fedora 44 keeps its
original compiler dependency names.

`rpms.yml` keeps Fedora 44's incremental package selection and `rpm-<package>`
artifacts. Every run also builds the complete Fedora 45 set in
`registry.fedoraproject.org/fedora:45`, using `rpm-f45-<package>` artifacts. Import,
collection, assembly and signing all enforce the selected release; a noarch RPM
is subject to the same release checks as an aarch64 RPM.

## Publication and channel state

The `fedora-release` input defaults to `44` in both `publish.yml` and
`deploy-snapshot.yml`. Automatic publication retains the Fedora 44 default.
Selecting `45` resolves only Fedora 45 artifacts and snapshots. Its first
publication requires the complete set, since there is no Fedora 45 base
snapshot to carry. A Fedora 44 snapshot cannot be used as its base.

Fedora 44 retains `testing-YYYYMMDD.N` tags. Fedora 45 uses
`testing-f45-YYYYMMDD.N`, with an independent sequence. Production signing uses
the same `testing-signing` environment and committed key for both releases.

The channels branch retains its existing `testing` and `stable` pointers and
adds `45/testing`. Every deployment authenticates and assembles all populated
paths, preserving Fedora 45 during a later Fedora 44 deployment and preserving
both Fedora 44 channels during a Fedora 45 deployment. Fedora 45 stable
promotion is rejected. Automatic image builds remain Fedora 44 only.

These changes provide the publication path. Merging, publishing, deploying and
machine rollout are separate operator actions.

## Validation

`tests/fixtures/fedora44-publish.json` freezes the plan and manifest generated by
starting main `7346ab2c1ce13176506243ed5bb398922bb73359` on deterministic inputs.
The source suite compares the new Fedora 44 output byte for byte with those
outputs. The Fedora 44 vendor-policy CI job also compares the starting-main
and current signers on identical real signed fc44 RPM bytes. Release tests cover independent tags, selected source pins, metadata
archives, artifact isolation and preservation of all three channel paths.

The `repository-fedora45` CI job consumes the complete current run's Fedora 45
artifacts. It authenticates every receipt, hash, native builder and RPM release,
assembles the complete source set, signs it with a temporary CI key, and serves
it over loopback in a Fedora 45 container. It installs stock graphics, Mutter,
Touch ID and power packages, then installs `aurora-repos` from the signed local
repository. The installed repository URL must resolve to `45/testing/aarch64`.
It installs the fleet bootchain exclude configuration at
`/etc/dnf/libdnf5.conf.d/90-aurora-fleet-bootchain.conf` and requires
`dnf5 upgrade --assumeno` to resolve without any fc44 package in the transaction
or newly installed inventory. Logs, the complete fc45 package list, effective
DNF configuration and signed manifest/metadata are retained as CI proof.

The temporary key is confined to the CI test. Production accepts the committed
Aurora key only; deployment rejects temporary-key manifests.
